# Central Heating System

Central controls and a responsive Home Assistant dashboard for local Tuya fan-coils supplied by two independently monitored heating-water zones. This installation deliberately uses `fan_only` to control fans directly; thermostat setpoints do not determine operation.

## v0.7.5: API read rejection recovery

Unacknowledged native status/configuration responses now follow the read-outage recovery path: keep HA selected, clear cached readings, and retry fresh reads after 60 seconds. Valid acknowledgements with invalid schemas still stop correction, and failed write confirmations remain conservative.

## v0.7.4: recoverable read outages and selected-owner buttons

A failed native read or a read-side deadline now pauses cloud writes, preserves the selected HA ownership and retries after 60 seconds. Cached native readings/corrections are not presented as fresh. Recovery requires both fresh native state and configuration plus the existing schedule, duration, RF/sensor, ownership and output checks. External manual/away/schedule changes or early cancellation still stop HA; explicit relinquish during an outage remains off after reconnection. A naturally expired owned override can recover from the current native schedule value without bypassing the 0.5°C step/cadence limit.

An unconfirmed mutation or post-write read-back timeout is not blindly retried or auto-adopted. Invalid native schemas, stale/invalid sensors, changed schedules and other safety faults retain conservative relinquish/expiry fallback behavior. A normal read outage leaves the confirmed native override to its real remaining duration, then miGo follows the fallback plan if HA still cannot connect. Local fan safety remains independent of cloud requests.

Home highlights the selected HA/miGo button with accessible pressed state, preserves HA selection with an explicit reconnection warning during read outages, and shows neither owner as selected while release is pending. Re-selecting already selected HA control is a no-op: it does not reset the native timer, duration or actuator cadence. Hot-water selection unavailable during a read outage is distinguished from a confirmed inactive schedule.

## v0.7.3: configurable correction interval below ten minutes

The correction interval accepts **60–7200 seconds**, including values below 600 seconds. The default remains 600 seconds; upgrades preserve existing saved values. Polish/English status and help show the actual configured interval. Each ordinary temperature change still stays within 0.5°C, with fresh native pre-write checks, crash-safe command spacing and the same expiry/ownership safeguards. Shorter intervals allow faster setpoint changes and more cloud commands; they do not guarantee reduced physical burner cycling.

## v0.7.2: full calculated target and next correction step

Home separately displays the current native miGo target, the full calculated target (`miGo measured + desired home target − weighted average`, before smoothing and limits), and the next limited actuator step. Values wrap on mobile and use Polish/English labels. No correction timing, smoothing, bounds or boiler control behavior changes.

## v0.7.1: miGo rejects redundant timetable transitions

The native API rejects consecutive identical `zone_id` values, including a repeated midnight target after the previous evening. Export now omits these no-op transitions while preserving the full editable HA plan, Monday baseline and effective weekly targets. Exact native payload read-back and all unrelated-schedule protections remain in place; logical read-back compares effective temperature changes. API rejection diagnostics identify the operation and numeric error code without including raw cloud messages or credentials.

## v0.7.0: acknowledged writes, active schedules and hot water

miGo may acknowledge a write with `body: []`; this no longer causes a Python attribute error. Reads still require an object body. Enabling correction first recovers a previously successful thermal write using exact, fresh read-back, including unchanged unrelated schedules, selection and timezone. It never repeats an unconfirmed thermal write implicitly or bypasses fallback verification.

For a single `NAVaillant` gateway with a uniquely linked source DHW schedule, explicit preparation creates a separate HA-owned `event` copy with hot water enabled in every zone (24/7 availability, not a boost or temperature change). Original heating/DHW plans and their links are preserved. Creation is persisted and recoverable across interruption/restart without duplicate copies. Unsupported modules, solar timetables or ambiguous links block creation. The original away/frost temperatures and boiler modes/protections remain unchanged.

Save/retry and enabling correction explicitly activate the confirmed HA heating and DHW schedules, verifying both selections and unchanged schedule content/modes. The bridge does not invent a `linked_schedules` write: where miGo does not link the new pair automatically, HA selects each typed schedule separately. Native away/frost/DHW-only modes and external manual overrides block activation; external changes to the owned DHW plan/selection stop correction rather than overwrite user intent. Passive startup never creates or selects either plan.

Event creation uses the `schedule_type` parameter supported by the [official Netatmo Home web client](https://home.netatmo.com/chunk-MDSWWFG7.js); event-zone structure is also described in the [installed miGo integration's API reference](https://github.com/tomahoax/ha-migo-netatmo/blob/aa522f3a106150a0c0672fab900393fd28519143/docs/api/reference.md#post-apisynchomeschedule). No native global `dhw_always_on`, water temperature, or DHW boost setting is changed.

## v0.6.1: miGo schedule-format compatibility

Thermal zones returned by miGo may include empty `modules` and redundant `rooms_temp`. The bridge accepts these only when the module list is exactly empty and every room/temperature alias matches `rooms`. Verified redundant fields are omitted from the documented schedule-write payload and normalized during read-back; source schedules are not mutated. Nonempty modules, conflicting aliases and unknown zone fields still block writes. Event/DHW schedules remain separate and untouched.

## v0.6.0: weighted whole-home comfort and real miGo schedules

The **Home / Schedule / Settings** tabs separate everyday temperature control from weekly programming and tuning. Home shows the measured weighted room average, effective desired target, target source, HA/miGo ownership, native reported target, proposed correction, limiter status, and native expiry. Polish remains the default, with English available in Settings. The existing Off/Manual/Adaptive selector is explicitly **fan-only**; it does not switch the boiler. Native miGo modulation remains responsible for the boiler, without HA bang-bang burner control. This does not promise that physical burner cycling disappears at very low demand.

This feature is optional. Without miGo setup, existing fan settings and saved central targets continue to work. No miGo target, duration, schedule, or mode is changed by passive installation/startup. Whole-home timed targets require miGo configuration; legacy room overrides retain their **local fan-only** scope and never change the global boiler target.

### Explicit setup

1. In Settings, select the installed `migo_netatmo` climate entity. Select up to six ambient room sensors or fan climate readings; weights default to 1 and 0 excludes a room. Heating-water sensors, generated water-temperature entities, the miGo climate reference and known miGo integration aliases cannot contribute to the average. miGo ambient remains the required reference at weight 0.
2. Use **Discover native schedules** to select the home, room, and source thermal schedule by name; opaque IDs remain an advanced fallback. Save settings. The bridge currently supports a **single-room miGo home** and simple thermal zones only, including the verified redundant miGo fields described above. Multiple native rooms, nonempty DHW modules/unknown zone fields, missing native away/frost values, or missing home timezone are rejected rather than guessed.
3. In Schedule, **Prepare native copy** creates a separate `Central Heating HA <entry id>` thermal schedule from the chosen native source and imports its desired temperatures, plus a dedicated DHW copy on supported Vaillant homes. It never adopts or edits the originals. This is an explicit creation action. Preparation is idempotent; repeating it does not replace saved HA edits. Saving a schedule before preparation is rejected without changing the desired schedule or browser draft.
4. Edit transitions using day/time/0.5°C target, add transitions, and copy a day to another day, weekdays, weekend, or all days. A Monday 00:00 baseline is mandatory; a target holds until the next transition. **Save and sync schedule** writes the actual **uncorrected desired weekly temperatures** to the dedicated native schedule and activates the HA heating/DHW plans. It does not emulate a schedule using manual commands. Sync preserves mandatory native Comfort/Night/Eco zones and exact native away/frost temperatures; original event/DHW schedules are not edited. Explicit schedule ID is always supplied, including when the managed copy is not selected. Read-back verifies targets, timetable, all unrelated schedules and selection metadata; pending/version/status show failures. **Retry native sync** confirms an interrupted successful write from its persisted expected payload or retries a safe unchanged baseline, then verifies activation. Unexpected external changes are not overwritten.
5. **Enable HA correction** recovers an interrupted successful thermal sync by read-back, explicitly selects both confirmed managed fallback plans, verifies selection, applies/verifies the shared native duration, and takes ownership. The native room must be in schedule/home mode and its reported target already within the configured output bounds. If the target is below 18°C, edit the desired fallback schedule into range and let native schedule mode report the in-range value before enabling; HA never silently jumps the initialization value past its ordinary slew limit. Exit native away/frost/DHW/other overrides yourself before enabling.

The integration uses the documented [Netatmo Energy schedule API](https://dev.netatmo.com/apidocumentation/energy#synchomeschedule): authenticated POST to the documented public `https://api.netatmo.com/api/createnewhomeschedule` and `synchomeschedule` endpoints, through the installed miGo API's authenticated transport. Declared query parameters are URL-encoded, with JSON-serialized `zones` and `timetable` arrays. The private miGo schedule-write endpoint is not invented. Runtime API incompatibility, OAuth scope rejection, cloud failures, or unsupported native schemas are reported and block confirmation/enable. **These paths have been validated against mocked API/schema round trips, not live writes to this installation.** Production activation needs an explicitly authorized native write/read-back check; no device writes or deployment were performed for this release's local validation.

### Correction, ownership and failure fallback

The only whole-home desired target comes from the saved weekly schedule, unless a timed global manual target is active. Apply target and minutes together; expiry/cancellation restores the *current* weekly target. Drafts for global targets, weekly transitions, and sensor weights survive tab changes and state refreshes. Persisted settings, schedule versions, manual deadlines, HA ownership, last command/time, verified native schedule/timezone and pending transactions survive restart. Native home timezone, including DST, determines weekly transitions even while HA/cloud is offline; it need not equal HA's timezone.

The correction is `miGo measured + (desired home target − weighted room average)`. The desired correction is elapsed-time smoothed (60-second default), bounded initially to **18–24°C** within miGo's native 7–30°C range, and rounded to 0.5°C. Saturation is visible. Small 0.05°C quantization hysteresis suppresses boundary chatter, with a finite two-interval escape so a persistent downward correction cannot remain held high. There is no integrator accumulating an elevated target. Ordinary commands are limited to **one 0.5°C step per configured correction interval**, from fresh native reported reality, even after a manual target/UI change. The default is 600 seconds (ten minutes), configurable between **60 and 7200 seconds**. Sensor events and five-second local ticks update averaging; direct reference/config polls default to **60 seconds**, configurable separately. Polling must be no slower than one third of the shared native duration, so renewal can be checked before expiry. A stalled cloud task cannot delay local fan Off/cold-water/room-limit reconciliation.

Room data must be available, finite, in a plausible ambient range, Celsius or convertible Fahrenheit, and have a fresh real `last_reported` timestamp (900-second default). Default weighted coverage is 100%; a configurable lower coverage threshold is explicit, not silently substituted. Invalid miGo reference, explicit room/thermostat RF unreachability, explicit stale thermostat-module `last_seen`/`last_message`, or insufficient coverage pauses correction and best-effort releases HA's identifiable bias. A gateway heartbeat does not validate a thermostat reading. If the API omits RF report timestamps, diagnostics say that only direct cloud-poll freshness/room availability was checked: a successful HTTP response alone is **not proof of a new physical temperature measurement**. After a safety-fault release, re-enable explicitly once the fault is resolved. Read-only connection outages instead preserve the selected ownership and retry automatically after 60 seconds, without using cached native data to authorize a command.

Native manual duration is a **shared home setting**, supported by the installed `number.elsnera_thermostat_manual_setpoint_duration` (5–720 minutes). The proposed starting value is **60 minutes**, configurable; the user's current 12-hour value is not overwritten on passive startup. This setting changes only on explicit enable or saving a changed duration while HA owns control. No independent per-command TTL/end time is supplied. Changing the native target resets its shared timer. Same-value renewal is attempted before actual expiry and must read back an extended `therm_setpoint_end_time` matching the confirmed shared duration; arbitrary identical commands are never assumed to renew. Same-value renewal may occur between ordinary correction slots but cannot change temperature or bypass the configured correction interval. Settings changes do not silently reset the native timer.

**Relinquish to miGo** stops HA corrections/renewal and cancels only a positively identified HA-owned room manual override via supported room `home` mode, verifying return to native schedule. A newer external manual/away/frost/off action is preserved: miGo already owns it. Unconfirmed cancellation persists as Release pending and is retried conservatively. Integration disable/unload best-effort relinquishes; a normal HA shutdown deliberately leaves the last native timer to provide fallback. If HA, network or power disappears, an already confirmed native override can persist for its **remaining shared duration**, then native miGo resumes the synced uncorrected weekly schedule. This is not instantaneous failover. If cancellation/command confirmation fails, diagnostics report uncertainty and the native timer may remain active. External changes to native targets, override deadlines, cancellation, shared duration, selected schedule, or managed schedule content cause HA to relinquish or block rather than overwrite native user intent.

The live comfort payload is excluded from recorder history to avoid storing the weekly plan on every small smoothing update. Dedicated water/room temperature history remains unchanged, and unchanged persisted comfort state does not trigger five-second disk writes.

**v0.5.0 smooths both Shelly water readings at every temperature**, including the fluctuations around 22°C. Each reader independently uses the median of up to three real reports followed by exponential smoothing with a **60-second time constant**. The lower median is used during the two-sample startup period. Smoothing follows elapsed time, so irregular report intervals and extra controller reconciliations do not change its strength. Dashboard temperatures and new chart history use the smoothed value, with one decimal displayed; control retains the underlying precision. Existing history is unchanged. No additional helpers or switches are needed.

Shellys can stop reporting when a temperature is steady. Between reports the filter continues toward trusted data without appending samples or refreshing report timestamps. The median can hold an older value for at most **60 seconds after the last accepted report**, then smoothing follows the last validated raw reading. This removes short dips while allowing a sustained change to settle even if no further reports arrive. Near the final value the filter settles within 0.01°C, allowing an exact 33°C reading to finish warm-water confirmation. A genuine warmup can take longer to enable fans because the smoothed reading must catch up.

An abrupt exact **85°C** reading is rejected as a suspected DS18B20 reset when there is no trusted raw baseline or it differs from that baseline by more than 5°C; a gradual approach to genuinely hot water is accepted even while smoothing lags behind. Isolated deviations over 10°C from the median are rejected, except that a valid raw cold-water reading must always stop its zone immediately. **A valid raw reading at or below the OFF threshold stops fans without waiting for smoothing.** New permission requires 30 seconds with smoothed and raw temperatures at or above the ON threshold. Rejected readings freeze smoothing and reset confirmation without extending the existing fault grace. Recovery after unavailability or an expired fault starts with a fresh filter baseline so old readings cannot bias the recovered sensor.

**v0.4.0 adds automatic Shelly backup in Adaptive mode.** If a primary water sensor is missing, unknown, unavailable, or outside the valid range, its zone immediately uses the other healthy Shelly. Brief rejected spikes still retain the primary's last accepted reading for up to **60 seconds**; if the fault persists, the healthy reader takes over. A backup must currently report valid data; a reader holding an invalid reading during its grace period cannot serve as backup. There is no switch to enable this behavior.

The affected zone follows the backup reader's own filtered temperature, 33°C/30°C hysteresis, and warm-water confirmation. It cannot inherit the failed primary's ON permission. Valid cold backup readings stop the fan immediately. Both readers unavailable stop Adaptive fans immediately; when both have rejected spikes, the existing 60-second grace can retain their previously enabled permissions before stopping. Readers never serve as backups for each other recursively. A valid primary report restores normal zone control automatically, with its own water permission and confirmation. Room limits, target overrides, fan-speed hysteresis, and Off mode retain priority. Manual continues to bypass water permission.

A prominent Polish/English dashboard warning names the affected zone and backup source, and the zone header shows the temperature actually used for control. One HA notification uses the installation's HA language, updates only when the backup mapping changes, and clears on recovery or when leaving Adaptive mode. `sensor.central_heating_status` exposes `backup_active`; each zone also exposes `water_source_id`, `backup_source_name`, `backup_source_sensor`, and `operating_water_temperature`. These are available for automations. Primary sensor diagnostics and history remain tied to their own reader, so a backup is not graphed as a recovered primary.

Sensor details show raw and accepted temperatures, report ages, rejection count, and faults. A stable, available HA reading is not considered invalid merely because its numeric value has not changed; the filter does not infer a hardware heartbeat from temperature changes.

Install and update from a computer on the HA network:

```sh
make check
make deploy
```

Requires Python 3.12+, Node.js for JavaScript syntax checking, OpenSSH, and the Home Assistant SSH add-on. `make deploy` defaults to `root@192.168.68.59:22` and prompts privately for the SSH password. It builds a versioned archive, uploads it, backs up the affected files on HA, runs `ha core check`, restarts HA, and verifies that the controller and room controls load. First installation starts in **Off**; updates preserve the selected mode. No passwords or API tokens are included in the repository or release archive.

For another SSH destination or key-based login:

```sh
python3 scripts/deploy.py --host 192.168.68.59 --user root --ssh-key
```

The installer keeps backups under `/config/central-heating-releases/`. It restores the previous configuration/component files if validation, restart, or the runtime check fails. For the runtime check, an existing active owner login session is required; the installer obtains a temporary API token locally on HA and does not export or save it. Existing unmanaged `central_heating:` or `lovelace:` YAML blocks require merging the supplied includes before installation. The installer only replaces its own component, site files, and marked configuration block.

To install a downloaded release manually, extract the archive in the HA SSH add-on and run `bash scripts/install.sh "$PWD"`. The release archive contains the integration, dashboard, site configuration, and installer. `make release` creates `dist/central-heating-system-vVERSION.tar.gz` and its SHA-256 checksum. The integration can also be installed as a HACS custom integration from this repository; the supplied dashboard/site configuration is still needed for this installation.

Invalid water thresholds are rejected. Missing room temperature blocks that room. Adaptive needs a usable primary or healthy backup water sensor; without either, its fans are requested Off. Manual bypasses the water rule. Conflicting zone labels stop the affected room. Unreachable devices are shown as unconfirmed and retried; the dashboard never claims a physical fan is off solely because an off command was requested. Removing a room's zone label requests Off before releasing control. Disabling the integration requests Off for its managed fan-coils.
